# Starter Output Rules

This document defines the quality bar for files generated by `go run ./tools/gwc start`.

## Rules

- generated starters must stay small and readable, with obvious file ownership
- generated starters must favor public framework packages over repo-internal helper wiring
- generated starters must be conventionally organized so teams can rename, move, or delete files safely
- generated starters must remain disposable; users should be able to replace generated code without breaking launcher ownership
- generated starters must avoid hidden coupling to monorepo-only paths or private build assumptions

## Expected Scaffold Shape

The scaffold should stay understandable on first read:

- one explicit wasm app entrypoint (`main.go`)
- one explicit browser shell (`index.html`)
- one explicit launcher metadata contract (`gwc-start.json`)
- one generated feature contract (`FEATURE_MATRIX.md`)
- optional capability-owned extras only when selected, such as `test/browser/` for browser tests

## Review Checklist

- can a team delete or rewrite generated files without reverse-engineering launcher internals
- does every generated file have a clear reason to exist
- does capability-driven generation add only the files needed for selected features
- does starter output remain app-owned instead of framework-owned after generation
