# Benchmarks & Performance

This page documents **how** GoWebComponents performance is measured and how to
reproduce it. It deliberately does not hard-code result figures: the numbers are
generated by `gwc bench` / `gwc wasm` and live in the checked-in JSON reports, so
they cannot silently drift from a stale copy pasted into prose.

## What is measured

Three independent measurement surfaces:

1. **Go microbenchmarks** — reconciliation, element construction, and SSR render
   paths, run with the standard Go benchmark harness and aggregated by
   `gwc bench`.
2. **WASM artifact size & startup** — `gwc wasm measure` records the compiled
   `.wasm` size and DOM-ready startup for a target package.
3. **Browser render comparison** — the `examples/testing/render-benchmark` app
   (driven by Playwright) compares first-paint and update latency against a
   React baseline across scripted render/update scenarios.

## Reproduce the numbers

From the repo root:

```powershell
# Go microbenchmarks -> docs/benchmarks/latest.json
go run ./tools/gwc bench -root .

# Compare a candidate run against the checked-in reference
go run ./tools/gwc bench compare -baseline .\docs\benchmarks\reference.json -candidate .\docs\benchmarks\latest.json

# WASM size + startup for a package
go run ./tools/gwc wasm measure -package .\examples\public\ui-render

# Browser render comparison vs React (Playwright)
go test -tags playwrightgo ./test/playwrightgo/examples -run TestExample201BrowserBenchmarkReport -v
```

The canonical machine-readable outputs are:

- `docs/benchmarks/latest.json` — the most recent local `gwc bench` run.
- `docs/benchmarks/reference.json` — the checked-in reference used for
  normalized scoring.

Read those files (or the `gwc bench compare` output) for the current figures.

## Methodology notes

- **Hardware matters.** Absolute latency and startup numbers are
  machine-dependent; record the CPU, OS, Go version, and browser version
  alongside any published figure. Prefer the *normalized* score from
  `gwc bench compare` for cross-machine comparison.
- **Warm vs cold.** WASM startup is dominated by fetch + instantiate + first
  DOM-ready; `gwc wasm measure` distinguishes artifact transfer size (raw and
  compressed) from execution.
- **Apples to apples.** The React comparison renders the same component tree and
  the same update scenarios on both stacks; the runner is in
  `examples/testing/render-benchmark` so the scenarios are auditable, not a
  black box.
- **No hand-typed numbers here.** This page intentionally omits specific figures
  so they cannot rot. Generate them with the commands above; a future CI note
  should flag when a published figure drifts from a fresh run beyond tolerance.

## Caveats

- Go→WASM has a larger cold-start artifact than hand-written JS; the framework's
  advantage is in steady-state reconciliation and zero-allocation update paths,
  and in shipping one language end to end. Weigh both for your use case.
- TinyGo (`gwc build -profile tinygo`) trades a constrained compatibility
  boundary for substantially smaller leaf-app binaries; measure both profiles
  for size-sensitive deployments.
